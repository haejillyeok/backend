# Sunset Domain

`해질녘(SUNSET)`은 호텔을 배경으로 한 웹 기반 모바일 반응형 멀티플레이어 게임입니다.
플레이어는 객실에 입장해 단어 게임을 진행하고, 게임이 끝난 뒤 함께 플레이한 손님 중
초대받지 않은 손님, 즉 AI 플레이어를 찾아내는 투표를 합니다.

이 문서는 캡처 기획안을 바탕으로 현재 프로젝트에서 먼저 공유해야 할 도메인 개념을 정리합니다.
구현 세부 API는 별도 API 문서에서 확정하되, 게임 상태와 WebSocket 진행 흐름은 이 문서의 기준을
우선 참고합니다.

## Product Shape

- 플랫폼 종류: 멀티플레이어 게임
- 플랫폼 형태: 웹 기반 모바일 반응형
- 주요 통신 방식: WebSocket 기반 실시간 통신
- 핵심 목표: 방에 모인 플레이어가 단어 게임을 진행하고, 종료 후 AI 손님을 찾아내 점수를 얻습니다.
- 테마: 해가 지는 호텔, 초대받지 못한 손님, 가면을 쓴 손님, 객실

## User Flow

1. 로그인합니다.
2. 로비에서 객실 목록을 확인합니다.
3. 객실에 입장하거나 새 객실을 만듭니다.
4. 객실에서 대기하고, 방장이 필요하면 게임 설정을 수정합니다.
5. 게임이 시작되면 닉네임이 가려지고 AI 손님이 추가됩니다.
6. 정해진 게임 규칙에 따라 라운드를 진행합니다.
7. 모든 라운드가 종료되면 플레이어가 AI로 의심되는 손님에게 투표합니다.
8. 단어 게임 점수와 투표 점수를 합산해 결과와 우승자를 표시합니다.

## Main Concepts

### User

로그인 가능한 계정입니다. 계정 ID, 비밀번호, 닉네임을 가집니다. 닉네임은 평소 표시명으로 쓰지만,
게임 시작 후에는 가면 처리된 표시명으로 대체될 수 있습니다.

### Guest

객실 안에서 게임에 참여하는 참가자 단위입니다. Guest는 실제 User일 수도 있고, 게임 시작 시 서버가
추가하는 AI 손님일 수도 있습니다. 게임 진행과 투표에서는 User보다 Guest 단위가 더 중요합니다.

### Uninvited Guest

초대받지 못한 손님입니다. 현재 기획상 AI 플레이어를 의미합니다. 대기방에 미리 표시하지 않고,
게임 시작 시 서버가 추가합니다. 플레이어는 게임 종료 후 누가 AI였는지 투표로 찾아냅니다.

### Lobby

객실을 찾고 입장하는 공간입니다. 로비에서는 객실 목록, 객실 번호, 게임 정보, 객실 이름,
현재 인원, 참여 가능 인원, 입장 버튼을 표시합니다. 객실 예약, 객실 찾기, 빠른 입장,
친한 손님 리스트, 게임 종류 필터 같은 기능이 연결될 수 있습니다.

### Room

플레이어가 입장해 대기하고 게임을 시작하는 객실입니다. 현재 Backend MVP의 객실은 최소한 객실 ID,
이름, 선택된 게임 종류, 참가자 목록, 게임 설정, 현재 상태를 가집니다. 준비 상태, 채팅, 빠른 시작은
확장 후보입니다. 객실 상태는 대기, 게임 중, 투표 중, 결과 표시처럼 명확한 단계로 관리되어야 합니다.

### Game Session

한 객실에서 시작되어 결과가 확정될 때까지의 게임 실행 단위입니다. 세션은 AI 손님 추가, 가면 처리,
라운드 목록, 턴 순서, 사용된 단어, 점수 기록, 투표 결과를 포함합니다. 클라이언트 화면보다 서버의
Game Session 상태가 최종 사실이어야 합니다.

### Round

끝말잇기 한판을 의미합니다. `max_rounds=8`이면 한 게임 세션 안에서 끝말잇기 판을 최대 8번 진행한 뒤
투표로 넘어갑니다. 라운드별 미션, 글자 수 제한, 폭탄 돌리기 같은 확장 규칙은 Round에 붙는 옵션으로
다루는 것이 자연스럽습니다.

### Cycle

한 Round 안에서 모든 Guest가 한 번씩 Turn을 가진 한 바퀴입니다. Cycle은 Round와 다릅니다. 예를 들어
3명이 참여한 1라운드에서 세 사람의 차례가 모두 지나면 1사이클이 끝나고, 라운드 종료 조건이 아직
만족되지 않았다면 같은 Round 안에서 2사이클을 이어갑니다.

### Turn

현재 단어를 입력해야 하는 Guest의 차례입니다. Turn은 시작 시각, 제한 시간, 현재 조건, 제출된 단어,
성공/실패 여부를 가집니다. 제한 시간과 시간 초과 판정은 서버가 권위 있게 처리해야 합니다.

### Submission

Guest가 Turn 중 제출한 단어입니다. 단어는 게임 종류별 규칙에 따라 검증됩니다. 예를 들어 끝말잇기는
이전 단어의 마지막 글자와 제출 단어의 첫 글자가 이어져야 하고, 이미 사용된 단어는 감점됩니다.
클라이언트는 시작 글자, 글자 수, 입력 가능 차례 같은 UX 검증을 할 수 있지만 최종 검증 경계가
아닙니다. 서버는 제출된 단어를 기준으로 차례, 제한 시간, 게임 조건, 중복 사용, 사전 존재 여부를
권위 있게 판단하고, 실패/패널티와 필요 시 추천 후보를 WebSocket event로 내려줍니다.

### Score Ledger

점수의 원인을 남기는 기록입니다. 빠른 입력, 기본 규칙 보너스, 앞글자 미스, 시간 초과, 중복 단어,
투표 성공과 실패를 합산하면 최종 점수가 됩니다. 최종 점수만 저장하지 말고 점수 변경 사유를 남겨야
결과 화면과 디버깅이 쉬워집니다.

### Vote

단어 게임이 끝난 뒤 AI 손님을 찾기 위한 투표입니다. 투표 시간은 20초로 기획되어 있습니다. AI를 찾으면
투표한 플레이어가 보너스를 받고, 다른 플레이어를 지목하면 감점됩니다. AI로 지목된 AI 손님도 투표 수에
따라 감점될 수 있습니다.

## Game Types

현재 Agent 서버는 `shiritori`, `chosung`, `contains` 타입의 단어 후보 검색을 지원합니다. 캡처의 주요
설명은 `shiritori`, 즉 끝말잇기에 집중되어 있습니다.

### Shiritori

끝말잇기는 앞 사람이 말한 단어의 마지막 글자로 시작하는 새 단어를 이어 말하는 게임입니다.

현재 Backend MVP에서 확정된 규칙은 다음과 같습니다.

- 첫 플레이어는 자유롭게 단어를 입력합니다.
- 다음 플레이어는 이전 단어의 마지막 글자로 시작하는 단어를 입력합니다.
- 이미 사용된 단어는 다시 사용할 수 없습니다.
- 제한 시간 내 입력하지 못하면 실패 처리됩니다.
- 플레이어당 기본 단어 입력 시간은 10초입니다.
- 성공한 단어 제출은 같은 Round 안의 다음 Turn으로 이어집니다.
- 단어 실패와 AI 답변 실패는 공개 판정으로 기록하되 현재 턴을 유지합니다.
- 제한 시간 초과는 현재 Round를 종료합니다.
- 남은 Round가 있으면 다음 Round의 첫 Turn으로 넘어가고, 최대 라운드 수를 채우면 투표로 넘어갑니다.
- 최대 8라운드가 설정되어 있으면, 즉 끝말잇기 8판을 마치면 게임이 종료되고 투표로 넘어갑니다.

현재 Backend MVP 점수 규칙은 다음과 같습니다.

- 단어 제출 성공: `+10`
- 앞글자 미스: `-5`
- 중복 단어 입력: `-1`
- AI를 맞힌 투표자: `+10`
- AI가 아닌 참가자를 지목한 투표자: `-5`
- AI로 지목된 AI 손님: 지목 1건당 `-5`

아래 규칙은 기획 확장 후보이며 현재 Backend MVP 로직에는 아직 들어가지 않았습니다.

- 5초 내 입력: `+10`
- 10초 내 입력: `+5`
- 기본 룰에서 4자 이상 단어 입력: `+3`
- 제한 시간 초과: `-10`
- 한 글자 단어 금지
- Cycle 종료마다 입력 시간 1초 감소

확장 규칙 후보는 다음과 같습니다.

- 글자 수 고정: 2자, 3자, 4자 이상
- 폭탄 돌리기: 정해진 시간이 끝날 때 차례인 플레이어 감점
- 라운드별 미션

## State Model

게임 구현은 화면 전환보다 상태 전이에 초점을 맞춥니다. 서버는 객실과 세션의 상태를 권위 있게
관리하고, 클라이언트는 WebSocket snapshot과 event를 받아 화면을 갱신합니다.

권장 상태 흐름은 다음과 같습니다. 현재 Backend MVP는 `room_waiting`에서 세션을 시작한 뒤
`starting/playing/voting/result`까지 진행하며, 결과 이후 같은 객실을 자동으로 다시 `room_waiting`으로
되돌리는 로직은 아직 구현하지 않았습니다.

1. `lobby`: 객실 목록을 탐색합니다.
2. `room_waiting`: 객실에 입장해 멤버를 동기화하고, 방장은 설정 수정과 게임 시작을 수행합니다.
3. `game_starting`: 서버가 참가자를 고정하고 AI 손님을 추가하며 표시명을 가면 처리합니다.
4. `round_playing`: 현재 라운드와 턴을 진행합니다.
5. `turn_active`: 특정 Guest가 제한 시간 안에 단어를 제출해야 합니다.
6. `round_finished`: 라운드 종료 조건을 계산하고 다음 라운드 또는 최종 투표로 이동합니다.
7. `voting`: 플레이어가 AI로 의심되는 Guest에게 투표합니다.
8. `result`: 점수와 투표 결과를 합산해 등수와 우승자를 표시합니다.
9. `room_waiting`: 일정 시간 후 같은 객실의 대기 상태로 돌아갑니다.

## WebSocket Focus

WebSocket은 사용자-facing 실시간 통신의 중심입니다. 서버는 다음 정보를 실시간으로 브로드캐스트해야
합니다.

- 객실 목록 변경
- 객실 참가자 입장, 퇴장, 설정 변경
- 게임 시작과 AI 손님 추가
- 라운드 시작, 턴 시작, 타이머 진행
- 단어 제출 성공/실패와 점수 변경
- 유효하지 않은 단어 입력의 패널티와 필요 시 추천 단어 후보
- 라운드 종료
- 투표 시작, 투표 제출, 투표 종료
- 최종 결과

현재 프로젝트의 WebSocket envelope는 `type`, `payload`를 기본으로 합니다. `/ws/realtime`은
ping/pong 연결 테스트용으로만 두고, 실제 게임 진행은 처음부터 `/ws/lobby/rooms/{room_public_id}`,
`/ws/match`로 나눕니다.
게임 진행 메시지는 순서가 중요하므로 이후 계약을 확정할 때 `request_id`와 `sequence`를 함께 고려해야
합니다.

레퍼런스 서비스 분석에서 가져올 만한 점은 로비와 실제 경기의 실시간 관심사를 분리해서 생각하는
방식입니다. 해질녘은 이 관심사를 처음부터 물리 WebSocket endpoint로도 분리합니다.
방 목록 조회, 방 생성, 방 입장, 방 설정 수정은 REST API가 맡고, `/ws/lobby/rooms/{room_public_id}`는 참여가
허용된 객실의 대기방 멤버 snapshot, 입장/퇴장, 설정 변경, 시작 handoff를 맡습니다. `/ws/match`는 게임 세션,
라운드, 턴, 단어 제출, 점수, 투표, 결과를 맡습니다. 빠른 시작은 `대기 -> 매칭 성사 -> 카운트다운 -> 경기 전환`처럼
명확한 상태 머신으로 관리할 수 있는 확장 후보입니다. 재접속 시에는 현재 객실 또는 게임 세션 snapshot을
다시 내려줄 수 있어야 합니다.

## Backend and Agent Boundary

Backend는 게임 상태를 소유합니다. 현재 MVP에서 방, 참가자, 객실 설정, 턴, 타이머, 사용 단어, 점수,
투표, 결과는 Backend의 책임입니다. 준비 상태와 채팅은 아직 public API/로직으로 확정되지 않았습니다.

Agent는 AI 손님의 단어 후보를 제공하는 역할입니다. Agent는 턴 순서, 라운드 종료, 투표, 마피아 규칙,
플레이어 점수 계산을 처리하지 않습니다. Backend가 현재 게임 상태를 바탕으로 Agent에 후보를 요청하고,
받은 답변을 다시 게임 규칙으로 반영합니다.

## Open Questions

- 객실의 최대 실제 플레이어 수와 AI 포함 총 참가자 수를 어떻게 구분할지 정해야 합니다.
- 게임 시작 권한이 방장에게만 있는지, 전원 준비 시 자동 시작인지 정해야 합니다.
- 게임 시작 시 추가되는 AI 손님 수를 방 설정으로 둘지, 서버가 자동 결정할지 정해야 합니다.
- Cycle 기반 종료 조건이나 입력 시간 감소를 MVP 이후 도입할지 정해야 합니다.
- 단어 입력 실패가 즉시 턴 종료인지, 제한 시간 안에서 재입력을 허용하는지 정해야 합니다.
- 동점일 때 공동 우승만 표시할지, 별도 타이브레이커를 둘지 정해야 합니다.
- 결과 이후 AI 정체와 가면 처리된 닉네임을 언제 공개할지 정해야 합니다.
- 로그인 전 게스트 플레이를 허용할지, 로그인 필수 게임으로 유지할지 정해야 합니다.
- 매치 중에도 `/ws/lobby/rooms/{room_public_id}` 연결을 유지할지, `/ws/match`만 유지하고 종료 후 로비로 재연결할지 정해야 합니다.
- AI 손님도 최종 우승자가 될 수 있는지, 플레이어가 AI를 찾지 못했을 때 AI에게 보상을 줄지 정해야 합니다.
- 5초 내 입력 점수와 10초 내 입력 점수가 배타적 구간인지 누적 보너스인지 정해야 합니다.
